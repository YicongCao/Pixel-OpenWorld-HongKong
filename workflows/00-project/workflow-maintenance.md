# 工作流维护与反馈闭环

工作流 ID：`WF-MAINTAIN`；版本：1.0；状态：本次目录迁移已做文档级验证，制作反馈的画面改善须逐批实测。

## 输入

用户需求或反馈、当前 Git 状态、[工作流目录](../README.md)、受影响研究／资产／街区证据。仅阅读必要主题；工具接口以当前 schema 和实际安装为准。

## 步骤

1. **定范围并选流程**：把需求转成一个可观察结果，选择主 workflow 和子流程；记录当前版本、起始提交和受影响阶段。纯研究／文档／工具维护用本流程；无合适专项流程时先创建最小版本，含输入、步骤、输出、验收与回退，登记目录。例行可逆操作沿用授权。
2. **找证据与基线**：复用 docs/data/references 的已知资料；时效事实和陌生技术查官方来源，记录日期、版本与限制。制作任务保存同机位／路线／输出配置的当前基线；文档任务保存结构与引用基线，环境任务保存安装版本和最小探测结果。
3. **定位问题所属步骤**：区分事实错误、资产缺件、镜头合同、材质／受光、摆放、活动或验证遗漏。事实问题更新静态来源并保留年代；一次性的店面宽度留在街区配置，跨街区可复用的错误预防才进入流程。美术压缩不得反写真实地图。
4. **修改方法和产物**：用户反馈必须回到所引用流程对应步骤，增加明确检查／失败回退条件，或澄清已存在但被漏执行的步骤；版本递增（结构／合同变化改主版本，检查补充改次版本）。再在授权范围内修产物。相同方法连续两轮无改善，回查参考／代码／导入，不盲调。文档任务用单一维护源与链接；工具任务使用相应已读技能，先做最小可回退验证。
5. **按影响范围验证**：制作按同一路线／机位对比，集成调用场景／光照验收；纯文档执行引用和生成页检查；工具配置验证连接、版本与最小操作。行为改变不能只拿截图通过，主观美术验收不得代替用户认可。未执行的步骤注明原因和待验证状态，不把时间过去当通过。
6. **闭环与交付**：把反馈、根因、规则修改、实际产物、证据、剩余问题关联在一次执行记录里；状态分“待实现／待复验／技术通过／待美术评审／已认可”。完成一个验证批次后检查 diff、commit、push、核对远程。推送失败保留本地成果并准确报告，不 force-push。

## 验收与回退

读者能从反馈追溯到流程规则、产物和实测；方法与事实各有单一维护源，无断链和虚构完成状态。无法验证的流程更新标为待验证提案；有回归时恢复上个有效配置，保留失败记录。文档迁移不能删改原始资产／数据／历史验证字节。
