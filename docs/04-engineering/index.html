引擎复评：HD-2D、组件复用与 Agent 工作流

2026-11-01 · v0.4 · 官方文档调研与工程判断；尚未验证框架、MCP、渲染和导出的完整组合。

环境实施更新：现已选择本机 Unity 6000.3.27f1 LTS 建立环境验证工程，工具／包的实测情况见 本地开发环境。以下比较保留研究时的判断；付费框架与 HD-2D 街区组合仍未验收。

当前建议

优先验证 Unity 6 + URP Universal Renderer（3D）＋一套可复用的 3D 角色／场景框架。Unreal 升为主要备选，Godot 3D 保留为开源备选。 TopDown Engine 的 3D 模式是首个框架候选，尚未购买、安装或锁定。名字里的 TopDown 不等于只能画平面瓦片；本项目要验证它的三维运动逻辑能否配合低角度像素表现。

v0.4 替代原来的“先纯 2D 灯光与分层虚化，必要时再改 2.5D”路线。真实体积、深度、台阶和镜头区从第一阶段进入架构。Unity 本身并不附送完整 RPG；推荐成立的条件是框架真正省下通用组件工作，像素／3D 混合呈现无需重写核心控制器。

评估顺序是：满足目标画面与通行空间 → 减少必要通用组件自研 → Agent 能完整修改、运行和诊断 → 本机导出与维护成本。没有剧情／战斗不构成淘汰 RPG Maker 的理由；但其最强的事件／数据库功能在本项目暂时不是主要工作量。

为什么暂时仍选 Unity

本项目需要的通用功能是稳定步行、输入、镜头、触发器、暂停、区域切换、位置保存和环境角色组织。先围绕这些功能选一套基础框架，不采购剧情、经济、战斗系统来充当“功能完整度”。

TopDown Engine 官方明确区分 2D 与 3D 控制器，并允许把角色逻辑根节点与视觉子节点分开；这支持“3D 控制器＋像素人物平面”的候选结构。官方镜头文档说明可接其他相机脚本，示例普遍使用 Cinemachine。这些只证明存在适配入口，不能证明低角度相机、当前 Cinemachine 版本、台阶和像素材质的组合已经通过。 角色结构、镜头、框架功能

先锁定一套输入、一套角色运动责任、一套镜头控制责任。官方包并非全部无条件叠加：AI Navigation 等仍是待核对的集成候选。若框架需要大规模修改源码才能支持楼梯或相机方向，其“省工”假设就失败，必须重新比较，而不是因为已经选过就坚持使用。

本机读取到 Unity Editor 6000.6.7f1，不把它误写为已安装的 6.3 LTS。正式版本在框架／URP／Cinemachine 兼容表明确后锁定；本轮没有安装、升级或修改编辑器。先记录现有版本，避免盲目追最新包。

Unreal 为什么进入主要备选

《八方旅人 II》有公开的 Unreal 制作访谈，是目标风格的生产先例。UE 的 3D 材质、相机和后处理工作流值得认真比较，但示例成功不代表我们的人员、资产和硬件已具备同样结果。开发者访谈

当前官方 UE 5.8 文档已经提供实验性的 Unreal MCP。 它可暴露 Actor、灯光、材质实例、界面检查和自动化测试等工具；需要相应 Toolsets，单启用 MCP 服务不等于所有功能已可用。官方同时说明功能仍有缺口，API／数据格式可能变化。因此不再用“缺少官方 Agent 集成”排除 UE，也不将实验能力视作稳定生产承诺。官方 Unreal MCP

UE 官方 Python 可自动化编辑器；运行时玩法依然需要 C++／Blueprint 等方案，不能把编辑器 Python 当游戏脚本。对于以文本修改、差异审查和重复构建为主的工作方式，Blueprint／资源资产的编辑和验证覆盖需要实际测试；这是一项工程成本判断，不是说 Agent 无法处理它们。官方编辑器 Python

暂选 Unity 的理由是 C# 与编辑器 API、框架候选及现有本机环境能较直接形成一次小规模验证。UE 反超的触发条件是：Unity 样板在关键画面或控制器上反复需要大改，而 UE 对应样板用现成能力能明显减少集成工作，且本机编辑、诊断、导出链路成立。不会为了比较而同时制作五套城市；必要时只将同一街角转成 UE 对照样板。HD-2D 不要求一开始启用 Lumen／Nanite 或光追。

Agent 集成要验证完整闭环

需要的是“改源码／场景 → 导入编译 → 运行固定路线 → 读取日志与截图 → 修复 → 导出”，不是仅连接 MCP 成功。实际覆盖、人工步骤与耗时应留下记录。

  • Unity：官方推荐 CLI / Pipeline，支持 unity command、unity eval 和 unity mcp；旧 com.unity.ai.assistant 内置 MCP 已弃用。具体方法与返回格式以锁定版本为准，本轮未连接或测试。官方迁移说明
  • Unreal：采用上面的官方实验性 MCP 与编辑器脚本候选，验证工具集是否覆盖实际素材和调试需求；不因文档出现接口就自动升级工程到对应版本。
  • Godot：官方 CLI 支持导入、运行、headless 与导出；文本场景适合代码审查。MCP 社区实现须单独核对维护与功能，不能称为官方集成。官方命令行、社区示例
  • GameMaker：官方 gm-cli 包含资源操作与 MCP，不能继续沿用“缺少 Agent 工具”的印象。YoYoGames 仓库
  • RPG Maker MZ：第三方 MCP 可编辑地图／数据库／事件；作者要求写 JSON 期间关闭编辑器，避免互相覆盖。自定义 3D 插件仍需另测，工具存在不代表插件兼容。第三方项目

渲染取舍已经收敛

采用真实 3D 深度，让道路、墙角、阶梯、雨篷和桥面提供前后关系。像素角色优先验证受光 alpha-clipped 平面与正确深度／阴影通道；透明对象需要额外检查。Unity 提供对应 Lit 材质和 URP 景深，艺术素材与相机仍需专门适配。Lit、景深

Godot 的 Sprite3D／AnimatedSprite3D 支持受光、billboard 与 alpha cut，可形成类似结构；原生相机景深依赖 Forward+ 或 Mobile，不支持 Compatibility。若换 Godot，应评估 3D 管线而非回到 Canvas2D 加后期伪造整个深度。SpriteBase3D、CameraAttributesPractical

GameMaker 的 surfaces／shaders 和 MZ 插件可以实现额外效果，但本轮未找到并验证一套能同时省下三维场景、分层通行、深度材质和相机工作量的完整组合。因此降低优先级，不能笼统声称这些引擎“做不了”。GameMaker Surfaces、MZ 产品

采购与锁定之前的通过条件

先验证一处横向街角、纵深支路、阶梯／桥下测试件、一栋分层商铺和白帽角色。画面分别测试白天、夜晚、景深开关；系统分别测试移动、镜头区、暂停、两区域往返与位置／楼层读档。Agent 必须能完成一次场景及材质修改后的编译、运行诊断和 Mac 导出。

记录直接复用、适配和新增代码各是什么；记录已安装引擎、渲染器、框架与包版本、人工干预步骤、帧时和显存／内存指标。通过后才锁定组合并批量制作资产；当前没有任何实测证明某引擎帧率更高、MCP 零故障或框架已经适配。

空间见 街网与镜头，像素规范见 美术研究，遮挡见 运行架构，样板见 实施验证。

渲染与运行架构

研究基线：2026-11-01 / v0.4。按主题整理；建议与待验证项不等同于已实现功能。

渲染与通行的具体方案

主选验证栈：Unity 6 + URP Universal Renderer（3D 路径）＋受光像素角色平面＋3D 街道几何与碰撞＋Cinemachine 镜头区。 不以 URP 2D Renderer、全局 Y-sort 或 2D 物理为基线。完整版候选比较见 引擎复评。

深度、遮挡与图层

人物逻辑根节点负责 3D 移动、碰撞与足底位置；视觉子节点是直立的角色平面，只绕竖轴朝向镜头，避免连脚底一起倾斜悬空。先验证 alpha clipping 的受光材质及正确深度／投影通道；透明玻璃、粒子与半透明淡出单独测试，不假设它们和不透明几何拥有完全相同的景深行为。URP Lit 材质

真实几何深度处理正常前后遮挡；近景屋檐、树冠和立面设置可选择的遮挡区域，仅在妨碍玩家阅读时淡出或抖动裁切。墙体背后的主角不应永久透墙显示。雨棚、屋顶、招牌、灯具与楼体分件，有自己的碰撞／阴影策略；活动楼层与渲染层并不是同一个字段。

角色投影须额外检验：面片旋转时不能让阴影剧烈跳动；必要时用独立简化投影代理或稳定接触阴影。模型／贴图法线是否值得制作，以夜间侧光样板决定；不是给每个路牌强制做全套 PBR。

光照与景深

路灯和橱窗的实际灯光负责照亮路面、白帽和人物；发光贴图负责招牌自身亮度，bloom 只提供光晕，三者分别调试。静态环境可比较烘焙光照／光照探针与有限动态灯；记录日夜切换时的兼容方式，避免仅改变太阳却保留明显错误的静态夜景阴影。不把光追、实时全局光照或体积雾列为 HD-2D 成立的先决条件。

URP 景深先验证深度输入，再平滑追随主角附近稳定目标的相机前向深度；可走区、重要标识和 UI 保持可辨。Gaussian 只能做远景虚化，树叶／雨篷等前景也要虚化时验证 Bokeh。本地 URP 17.3 的 DOF 深度转换存在正交限制，优先弱透视样板；这项源码判断尚非实机结果。透明边缘、白帽漏色、焦点抖动与性能分别检查，并提供关闭景深选项。具体步骤和证据见 HD-2D 镜头与渲染实施。Unity 6.3 官方模式说明

坐标与移动

地理空间继续保留原坐标；游戏布局另存：game_x = east、game_z = north、game_y = elevation，初始采用 1 Unity 单位对应 1 个设计米。HKPD 高程先扣除明确记录的本地高程基准，再映射；若艺术压缩发生，写独立转换记录，不改源数据。右侧示意图的 0.55 压缩不作为默认世界缩放。

输入根据相机的地面投影变换为世界移动；镜头过渡期间需锁定或平滑插值输入基底，避免按住右键时突然折返。转场触发器有进入／退出余量，防止在边界反复切镜。楼梯和坡面使用 3D 控制器的坡度／台阶参数；人行导航使用分层可行走面及明确跨层连接，避免 NPC 穿楼或把桥上桥下当同一路面。

Cinemachine 提供镜头间自定义过渡，但街段触发、输入连续性、遮挡与聚焦属于本项目适配责任；还需确认框架所用 Cinemachine 主版本。官方镜头过渡

最小技术结构

离线加工链：真实 GIS → 选段与证据核对 → 独立游戏布局 → 模块化 3D 场景＋像素资产 → 引擎场景。运行时只读加工后的资源，不联网查询 GIS，不依赖旧仓库，也不加载全港 GPKG。

先复用框架与引擎已有组件，再写香港街道需要的适配：

  • 运动与输入：采用一个 3D 控制器，移动根节点与像素视觉子节点分开；验证坡面、台阶及相机相对输入，避免并行控制器争抢位置。
  • 镜头：Cinemachine 或框架兼容的相机负责跟随与过渡；项目配置街段镜头区、切换余量、焦点和遮挡处理，转场期间输入不能突然反向。
  • 区域：首街角常驻；相邻街段先允许短淡入淡出，是否预载／流式由实测决定。按沿街场景和连接口分区，不以旧 64×64 瓦片强制分块。
  • 资产：路面、体积立面、雨棚／屋顶、橱窗与灯具分件；角色以 alpha-clipped 受光平面为起点，检查深度、阴影和半透明边缘。
  • 楼层与导航：3D 碰撞、可行走面和明确跨层连接；桥上桥下独立，投影相交不建连接。人群路径必须遵守路口、队列和活动占用。
  • 状态：复用可用的保存设施，项目定义区域、世界位置、朝向、楼层、活动时间、设置和版本；框架库存存档不是完整世界存档。
  • 街道活动：把人物、车辆、道具、服务门、等候锚点与空间声源绑定成活动；近处完整模拟，远处简化，合理进出场。

保留 source_id（不可变来源）、place_id（现实地点）、asset_id（复用资产）、instance_id（本次放置）四种身份。世界资产字段候选为 chunk_id、level_id、position_m_xyz、foot_anchor_local、collision_shape_3d、occlusion_group、camera_zone_id、source_ids、geographic_edit_note。真实高程与游戏高度转换显式记录，玩法楼层、渲染深度、光照分组不能混用。

资源读取、实例化、碰撞创建和首次着色器使用需要分别测量。加法加载支持不等于已解决城市流式；首版不需要 ECS、服务端或全城人口常驻模拟。深度、光照和景深见本篇上方；像素资产规范见 HD-2D 美术。

第一候选：像素管线，能复用什么

固定检查版本为 f08bc6b。版本直接核对 ProjectVersion、manifest 与 MIT。

已阅读 PixelRendererFeature.cs：使用 RecordRenderGraph，在 AfterRenderingPostProcessing 后复制全分辨率颜色，再低分辨率取样、描边、合成和放大。深度／法线是输入依赖，效果所需纹理由 RenderGraph 创建。可以少写一套渲染 pass 生命周期、采样与合成逻辑。

但它先画全分辨率场景再降采样，不能据此推导出减少主场景几何或光照开销；还会增加 pass 和深度／法线需求。640×360 是作者默认值，不应变成本项目全局约定；先比较 960×540、1280×720 与原生画面，保留中文路牌和白帽的可读性。这些是本项目实验档位，尚未测量。

已阅读 IsometricCameraController.cs：Awake 会强制 orthographic=true，像素尺寸由 orthographicSize 计算，还调用旧 UnityEngine.Input。不能直接挂到当前相机：它会改变弱透视和景深前提，并和 Cinemachine 的变换控制竞争。只把屏幕网格对齐／UV 补偿作为待移植思路；透视下不同深度像素尺寸不同，需要另外验证，不能把正交公式照搬。

作者的 toon、草与云影更接近全 3D 像素化。香港样板需要像素人物和有体积的纹理建筑，不能用全屏像素化替代立面美术。先试渲染部件；不搬地形、草、相机、输入、项目设置和所有包清单。MIT 通知在真正引入代码时随采用目录保存。

旧 HD-2D 示例：哪些代码值得看、哪些应跳过

检查 8145946，实际是 URP 12／Cinemachine 2.8.9，不是 Unity 6 模板。

  • SpriteShadow.cs 设置 Sprite／Tilemap Renderer 的受影和双面投影；说明这些职责可以复用 Unity Renderer 配置，不必先发明影子系统。正确帧裁切、材质 ShadowCaster 与自阴影仍要单独验证，开启标志不保证效果正确。
  • SpriteQuad.cs 把 Sprite 的纹理／UV 交给 MeshRenderer。它访问 .material 和 .mesh，会涉及实例化；SetSprite 内还使用字段 sprite 判断传入对象。可参考转换方法，但不替换我们现有的图集＋MaterialPropertyBlock 播放器，先衡量是否真的少代码。
  • SpriteSorting.cs 把世界 Z 乘 16 写入 sortingOrder。它无法表达天桥、站口、台阶与上下层遮挡，不采用。
  • HD2DCharacter.cs 依赖 TeamMingo 类型，并直接增加 Transform 位置。不是可直接替换的带 3D 碰撞通用控制器，保留当前 CharacterController／Input System。

仅局部采用自有脚本时保留 MIT，素材目录另核查。不要把该仓库整套场景和外来美术搬进生产工程。

行为组件与遮挡备选

UnityHFSM 提供层级状态、转换和退出时机协调；UPM package.json 当前为 2.3.0，许可证 为 MIT。这次只核查文档／包／许可，未深入运行时实现或运行测试；实际采用须再锁定 tag 或 commit，不能长期跟踪浮动 upm。

适合公交的 Approach → Stop → DoorOpen → Alight → Board → DoorClose → Depart，以及收货的准备、搬运、交付、清场。它减少状态机基础代码；不会自动提供香港车道、候车容量、上下客同步、站口寻路或存档语义。寻路继续使用已装 AI Navigation，数据配置仍由本项目负责；不因引入状态机另做一个可视化 RPG 编辑器。

Chishikii 的 README 明确区分功能：outline 已适配 RenderGraph，但 blur 和 desaturation 尚未适配。适合研究局部受控的主角轮廓提示；本次没有逐行审查其 shader，不把全部功能称为 URP 17 可直接使用。遮挡辅助应限于短暂、必要场景；正常情况下仍遵守 3D 深度，不永久穿墙显示角色。

对 v0.1 实施规划的具体调整

先建立独立渲染实验副本，不改变地理、控制器和正式样板。比较“当前画面／只加描边与放大／加补偿”三组，保存相同路线、镜头、1080p 的独立 Player 证据；景深分别开关，并观察玻璃 A1、树冠、白帽边缘、繁中店招及前后景。效果选择必须考虑整体 HD-2D 风格，而非某张截图的像素数量。

复用验收包括：不强制正交、不和 Cinemachine 竞争、不切换回旧 Input、不把 UI 全屏降采样；白帽的颜色／深度／阴影裁切一致；多相机状态不互相污染；无 RenderGraph 读写冲突、黑屏或构建 shader stripping；记录新增 pass 和真实帧时，不能宣称降分辨率天然加速。先分别测试，再决定采用代码范围和署名。

行为原型优先用 UnityHFSM 做一条公交循环和一个目的地行人，再连到 AI Navigation。验证重复三轮：车门未开不能上客、队列容量有限、演员有退出点、重置不重复生成。它替代通用状态机骨架，不替代现实站位核实与生活编排。

本次成果仅为研究与采用建议：没有复制第三方源代码／美术、安装新包或修改运行时。后续真正引入时按固定版本、独立命名空间、第三方通知和可关闭的组件接入；不 fork 整个别人项目作为新的主工程。
