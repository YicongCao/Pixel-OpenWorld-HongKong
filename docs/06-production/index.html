项目远期 Roadmap

2026-11-01 · 产品路线规划 r1 · 状态：路线拟定；V1-00 环境验证完成，V1-01 选段／实景及概念研究已推进，街区实机制作未开始。

先做一条值得步行和停留的香港街道，再把同样的质量扩展为相连街区，最终形成可持续扩充的九龙 HD-2D 步行世界。 地图扩大与生活丰富必须一起推进，不以地标数量代替体验。

本文的 v0.1、v0.2 等是拟定的游戏版本；既有“策划 v0.4”是文档版本，不表示游戏已发布到 v0.4。首版具体任务见 v0.1 实施规划。

起点与终点

已有可复用成果是：香港选区地图与行人／公共交通数据、来源记录、街区与生活目录、五张早期探索图及首街区三张新参考图、引擎复评、章节文档和 Git 工作流。另已建立 Unity 环境验证工程；仍无合格街区生产资产、已验证步行图或街区性能结论。

v1.0 的目标是经过验收的九龙步行路线网络：包含尖沙咀／尖东、西九及向佐敦—油麻地—旺角延伸的代表性街段；明确可走边界与连接，支持随时停留、往返、保存和继续。它不等于研究窗口内每栋建筑、每条巷子都已复刻。最终开放街段清单随生产测速和地图证据确定，不能把背景或未开放地区算成可探索面积。

主角、HD-2D 表现、真实街区关系和日常生活是持续约束。剧情、战斗、经济系统、联机、玩家驾驶／乘车不进入这份 Roadmap；之后若用户提出，再单独立项。

以什么决定扩大地图

每批街段登记以下指标，用于决定下一批规模；数字从实际制作开始累计，当前没有已测基线。

  • 体验完整度：真实路线能走、能返回、可停留；入口、站点与活动有合理空间关系。缺失一项就不是完成街段。
  • 制作成本：分别记录资料核对、贴图、建模、场景配置、活动适配、修复的有效工时；等待服务或用户审阅另计。
  • 复用情况：记录直接复用、参数变体和新增独有资产；比较同类、相近长度和密度的街段，不以大空地与复杂街角比较效率。
  • 质量问题：区分地理错误、像素／材质不统一、镜头迷向、通行错误和活动不同步；重复出现的问题先改规范或组件。
  • 运行预算：记录分辨率、可见 NPC／车辆、阴影灯、活动与区域数。性能恶化先定位成本，不自动通过删除全部人群来达标。

v0.2 完成后，只有第二街段比首段减少重复制作、且没有显著损失生活质量，才允许进入成片扩展。若主要工作仍是逐栋重新生成、手工纠错，优先修资产颗粒度和流程。

排期与资源的滚动方法

当前没有 Unity／框架／资产生产的完整实测，不能给整个九龙一个可信的固定完成日期。沿用已撤回的 8–17 人日估计也不合适；这份 Roadmap 采用完成门槛驱动排期。

  1. v0.1 先执行“选段取证＋环境闭环＋灰盒镜头”三个任务包，得到地图复杂度、可用组件、实际导出路径和基本画面成本。
  2. 以首栋商铺／首组人物动画／首个活动的实际工时，估算剩余资产与场景工作，并单列集成和修复，不用生成图片张数代替完成工作量。
  3. v0.2 再用第二街段的数据更新每类街段的区间估算；此后每批排期只覆盖下一批确定范围，不预先承诺所有远期街区日期。
  4. 当前资源假设为用户负责方向与主观画面验收，Agent 负责取证整理、编码、自动化和可执行验证；像素修订／模型调整是否需要人工参与，以样板质量决定，不假设能够全自动达到目标。

需要购买的框架、素材、服务或发布成本，在明确商品和预算后单独处理；这份规划不等于采购、引擎迁移或公开发布游戏的授权。已有文件修改后的 commit／push 授权继续有效。

v0.1 实施规划：一条会生活的香港街道

2026-11-01 · 首个可玩版本计划 r2 · 状态：已执行 实施批次 01，有连续路线、灰盒和 A1 实机样板；V1-03 美术待反馈，完整 v0.1 尚未完成。

首版交付是一段可反复行走、可停留观察、有真实香港依据的 HD-2D 小街区，以及能重新构建它的资产与工程。 玩家可控制白帽小巫师横向走过主街、深入支路、观察站口和公交活动、保存退出再继续。目标是一次约 5–10 分钟的探索与观察体验；这是设计目标，不是靠放慢速度或强制等待拉长内容。

它同时验证三件事：画面是否达到目标、街道是否自然可走、数据到实机的制作方式是否能复用。技术灰盒是中途检查点，不作为最终 v0.1 发布结果。远期扩展见 Roadmap。

1. 选段与范围冻结

最新首选为 弥敦道—海防道／A1，取代早期广东道街角优先建议。以下保留候选比较依据。第一项工作是比较具体边界，而不是马上把现有概念图做成场景。 现有资料尚未证明原来的 80–150 米主街＋30–60 米支路范围能同时容纳真实巴士站、港铁口及完整通行路线。

  • 候选 A：广东道—海防道街角，以连续商业立面和横向主街为重点。
  • 候选 B：海防道另一端与弥敦道相关街段，以站口及交通活动的可达性为核对重点；是否合适须按实际站位、过街和街景证据确认。
  • 选择标准依次为：真实连续步行路线、可读的横向／纵深空间、可核实的港铁口与巴士停靠点、参考图片覆盖、独有资产制作量。此处是候选比较，不是已核验的具体出口或班次推荐。

在 V1-01 形成唯一 block_id 和边界：精做核心为一个街角＋一条纵深支路，最多增加一个有真实连接的必要短段；首版最多两个可走场景单元。视野外楼体作为背景，不计可玩面积。

如果这个范围仍无法同时满足所需交通节点，应重新选段并说明取舍，不能把站口／站牌搬到商场旁，也不能默默把首版扩成整个尖沙咀。无真实依据的坡道／天桥测试件留在独立开发场景，不进入正式街区。

3. 技术与制作策略

沿用 引擎研究 的 Unity 3D／URP 候选方向。先核实本机版本、现有授权和框架兼容，再锁定一套控制器、一套输入责任和一套镜头责任。没有框架授权时先做可替换的最小白盒验证；这不等于正式决定手写全部通用系统，也不因规划而自动采购。

先完成“能走的灰盒”，再用真实街景＋布局引导图生成同机位概念，随后验证一栋商铺的生产资产。这样能在批量生成前发现相机看不见入口、双侧建筑遮挡或纵深太窄的问题。imagegen 输出、手工修订和生产采用版本分别管理，提示词与输入参考必须归档。

初始制作量只用于发现成本，不能作为任意修改地理的配额：约 4–6 个可复用立面／转角模块、1–2 个独有识别界面、1 套路面／路缘／标线、约 12 类基础街道道具、1 套主角动画、少量 NPC 外观与行为动作、2 类小车表现、1 辆巴士及所选活动需要的道具。港铁口、巴士站和实际铺面以核实清单为准；新增独有项必须记录成本。

基础路面和规则墙体先使用 Unity 模块；需要复杂轮廓、阶梯／站口、车辆或专用 UV 时再用 Blender。不要把所有物件都走一次复杂建模链，也不能用一张整街贴图替代可行走的场景。

6. 主角验证动线

V1-01 核定实际位置后，以同一份路线配置驱动重复验证；以下 A–F 是功能锚点，不是未经核实的现实地点。

  1. A：从可识别的街口开始，沿横向主街走到 B，经过玻璃／招牌受光区及近景雨篷，检查人物深度、脚底和遮挡。
  2. B → C：走入真实纵深连接，遇到有人停留或搬运的局部空间，验证绕行和镜头方向；有已开放的真实台阶时走一遍。
  3. C → D：到核实的港铁口附近，观察人流由入口进入人行网络，确认角色不会从墙中出现或堵在梯口。
  4. D → E：通过正确过街位置走向巴士站，观察车辆停稳、车门、上下客和队列变化；玩家只能步行经过。
  5. E → F：观察所选非交通微活动的完整过程，停留两分钟后按同一路线返回 A。
  6. 在 B、D 和 F 分别保存／退出／继续；再在镜头区或场景边界往返 20 次，检查方向、楼层和对象归属。

具体路线可能调整为相反顺序，但所有功能锚点和真实连通关系必须保留。独立阶梯／天桥测试场景的通过记录另存，不能把测试件截图当作正式街区。

7. 首版验收与可测负载

沿用 通用验收，本版补充以下固定条件；全部为目标而非已测结果。

  • 基本功能：键盘操作、暂停／继续、设置与存档可重复使用；路径不穿墙、不坠落、不陷入不可恢复卡死；镜头切换不反转持续输入。
  • 风格：同机位比较真实参考、概念与实机；主街横向、支路纵深、建筑体积与像素人物成立。生成伪字、异常尺度和明显写实／像素混搭必须修正；用户主观认可单独记录。

  • 配置基线：正常测试档以 12 名可见 NPC（包含候车、站口和活动演员，不含主角）、2 辆行驶小车、1 辆活动用货车和 1 辆巴士为初始负载；货车仅在选择装卸时出现。繁忙档比较 24 名 NPC、4 辆小车及同等活动车辆。具体点位容纳不下时调整出现时序，记录实际峰值，不把密度目标凌驾于地理。
  • 性能：在当前开发 Mac 的独立 Player、1080p、已记录质量设置下运行至少 10 分钟；暖机后帧时 P95 ≤16.7 ms、P99 ≤25 ms，常态移动不出现 >50 ms 的明显停顿。繁忙档记录差异，不假称同样达标；720p／1440p 与非整数窗口检查像素、文字与画面稳定性。
  • 内存与状态：比较第 2–5 分钟和第 7–10 分钟同一路线的内存与对象数；重复进入／退出后不持续累积。位置／楼层与活动恢复不能生成重复人车。
  • 情境对照：白天／夜晚检查受光与景深；晴雨及工作日／休息日验证预设至少改变一项合理的行为或停留安排。它们不需要同时形成完整连续日历系统。

若正常档无法达标，先记录瓶颈并优化阴影、透明层、活动更新和可见范围；不要悄悄关掉全部人群或降低分辨率后仍引用原条件的性能结论。影响地理、可走性、核心风格、状态恢复或必需活动的缺陷属于阻断项；新增装饰不能抵消它们。

生成式工具用于概念、色调和局部方案探索。进入生产需要像素编辑、统一调色板、模块建模与 UV、足底锚点、深度／阴影检查和遮挡分件。不要把整幅 AI 街景按屏幕平铺：这样会失去转角、碰撞、通行与邻接一致性。

生成输出与手工修订分别放 generated/ 和 authored/；构建脚本只刷新 generated。已精修图块通过清单选择，重跑脚本不能覆盖 authored。这个约定直接针对旧项目程序化生成覆盖手工精修的风险。

首街段通过后，用同一套素材做第二条相邻街段。若主要时间仍用于逐栋重画、几乎没有模块复用，就暂停扩区，先修改资产颗粒度与镜头。此时新增更多自动化工具通常不能解决问题。

执行工作流

完整采集、真实街景图生图、贴图、按需 Blender 建模及 Unity 导入步骤由 街区还原工作流 维护；本章记录制作建议，不复制一份易分叉的执行规则。

专业资料支持的具体制作方法见 HD-2D 素材建模与拼装 SOP：镜头合同、角色小样、模块接口／UV／贴图、模型导出、预制体拼装和实机门槛。角色方向与动作 和 镜头／受光／景深 分别维护细则；旧预算里的四向与配色数量不是最终制作标准。

香港 HD-2D 街区还原工作流

本文件维护街区制作流程，由根目录 AGENTS.md 引用；常驻项目约定与提交／推送规则统一在该入口维护。用户要求还原一个香港街区时，执行下面的完整链路；仅研究、仅修图或局部修复的请求按指定范围执行。沿用已有授权，例行可逆操作不反复确认。不要把本文件理解为现在就开始制作未指定的街区。

文中的代码路径均相对于仓库根目录；../game-research 指仓库的同级工程，不相对于本文件所在目录。

项目目标与固定边界

  • 制作以《八方旅人》为参照的 HD-2D 香港步行世界：像素角色、像素纹理的立体街景、横向主街、纵深巷道、真实遮挡、克制的景深与光照。主角是三角白帽、白衣小巫师。
  • 核心体验是沉浸式香港街道生活。地标、普通建筑、交通设施、人群、劳动活动、声景、时间与天气共同验收；不以空建筑和随机行人替代城市生活。
  • 首版无剧情、战斗或玩家可乘交通。汽车行驶、公交靠站、NPC 上下车和站口进出属于环境模拟，不自动扩展为玩家驾驶、乘车或完整站内空间。
  • 当前实现目标为 Unity 3D 空间与 URP 3D 渲染路径；框架、包版本及性能仍须验证。参考 docs/01-vision/vision.md、docs/03-hd2d/street-camera.md 和 docs/05-street-life/street-life.md。
  • 保留真实街道方位、路口顺序、建筑街侧、海陆关系和通行楼层。镜头方向与地理方向分开；不可为了构图搬动真实地标或虚构连接，不把整个尖沙咀夸张成山坡。

0. 开始任务与确定交付范围

  1. 读取本文件、AGENTS.md、docs/README.md、docs/Agent.md 与 docs/Skill.md，涉及数据先读 data/Readme.md 与 data/Agent.md，涉及资产先读 assets/Readme.md 与 assets/Agent.md；再按任务读取对应主题、目标街区已有资料与未完成记录，检查 Git 状态和远程。复用现有工作，不从零重复采集。
  2. 将用户地名落成稳定 block_id、地理边界、目标街段、出入口和一条玩家验证路线。区分本次可走区、仅可见背景、后续扩展区；边界未指定时先选择可独立验证的小街段并说明假设。
  3. 明确视角、主要街道方向、参考年代、时段／天气和本次必须出现的生活活动。只有缺失信息会改变关键地理或交付范围时才询问；其余取可撤回的初值推进。
  4. 在 docs/08-blocks/<block_id>/plan.md 记录本次范围、步骤、依赖、验收与缺口。后续每阶段更新实际状态，不能把计划标为完成。

1. 从 game-research 建立逻辑骨架

  1. 只读检查相邻 ../game-research 的香港数据目录、目录索引、README 和 manifest；本项目先读 data/hong-kong/README.md。优先复用本仓库已有对应快照，仅追加所需缺项与更新。
  2. 按选区和必要缓冲提取道路、建筑脚印、POI、地形／高程依据、三维行人路径、公交／小巴站点与线路、港铁站点／出入口／街道图／布局图，以及相关城建设施资料。拷贝所需原件或可追溯派生数据到 data/blocks/<block_id>/，不让运行时依赖相邻仓库。
  3. 每个来源记录来源仓库相对路径、发布者／原始 URL、快照及采集日期、SHA-256、许可／署名说明、CRS／单位／高程基准、筛选规则及覆盖缺口；派生结果另有输出哈希与复现命令。现有公共数据可按源 ID 引用，不为每街区重复复制完整大包。
  4. 公交使用完整表，不把增量表当全量；保留营办者、线路方向、站序和站位。区内截取站序不等于完整线路，也不是车辆实际行驶轨迹。必要时保留区外相邻站作上下文，明确截断位置。
  5. 经纬度、EPSG:2326 米制与 HKPD 高程分开；三维行人路径不是地形 DEM。楼梯、扶梯、桥、隧道、升降机保留 level_id 和有证据的连接；不能因平面相交或距离近就自动互通。
  6. 生成带北箭头、比例与来源的逻辑骨架图：可走区域、建筑脚印、道路／车道候选、路口、交通站位、跨层通道、地标及服务门候选。人工核对真正可通行关系后，另存游戏布局与压缩说明。

完成条件：数据能追溯，逻辑骨架能够解释主角从哪里走到哪里、车辆在哪里运行、人群从哪里出现或离开；未知位置明确标为待核实，不用生成图补地理事实。

2. 在线采集与核对真实街景

  1. 查询目标街区的实际街景、官方设施／运营商图片、公开可访问的街道照片及必要的历史资料。地图和运营商官网核对身份、地址、出口和站位，照片核对立面、街道家具、视线与生活细节。
  2. 参考至少覆盖本次关键位置：主街双侧立面、连接巷口、街角转折、重要高差，以及涉及的公交站／地铁口；有资料缺口就缩小或标记该部分，不拿其他街区图片冒充现场。
  3. 实际查看图片，记录可确定的位置、朝向、拍摄／发布年代和可信度。区分同名地点、同一建筑不同立面、历史照片与当前状态；不将搜索缩略图标题当成位置证明。
  4. 在 references/blocks/<block_id>/index.json 记录原网页 URL、原图 URL（可得时）、作者／发布者、日期、位置／方向、用途、许可或再分发状态、文件哈希及对应 source_id/place_id。
  5. 可保存且可入库的参考原件放同目录。仅能查看或不宜再分发的图片保留链接和观察记录，不将受限原件提交远程；临时文件放被忽略的 .local/。遵守来源访问条件，不绕过登录／下载限制。
  6. 用照片修正“待核实”的资产与活动候选，注明证据；不以主观印象覆盖原地图。人群身份、日程、卸货频率和雪糕车驻点不是 GIS 自动提供的数据。

完成条件：每个关键视觉锚点能对应实际街景；参考图与逻辑骨架之间的冲突、年代差异和遮挡缺口有记录。

3. 用实际参考图生成 HD-2D 概念图

  1. 制作一张简化布局／镜头引导图，标注主街、支路、建筑街侧、高差、相机方向、近中远景和主角路线。必要时先用简单灰盒检查视线，避免要求图像模型从复杂地图自行推理全部几何。
  2. 调用 imagegen 前读取其技能和当前工具说明，实际查看准备输入的参考图片。使用工具支持的参考图参数传入真实街景及布局图；不能只写“参考某街景”就声称完成图生图。无法传入必要参考时，记录缺口，不把纯文生图标成基于照片的还原。
  3. 明确哪些输入负责地理布局，哪些负责建筑外观，哪些负责风格；构图只在已核对骨架内调整。先生成与目标日常游戏镜头一致的一幅，再按需要探索同机位昼夜／天气变体。
  4. 提示词必须包含下面的要素，按实际街区替换，不把所有香港元素硬塞进一图：
任务：把参考图中的 [真实街区/街段] 转化为用于 Unity 制作的 HD-2D 游戏场景概念。
依据：布局图控制道路、建筑街侧、路口顺序与高差；街景图 A/B/C 控制指定立面、店铺与交通设施。保留这些约束，不移动或新增地标来改善构图。
视角：接近《八方旅人》的日常探索镜头；固定低斜俯视、弱透视，俯角以约 25–35°为起点；非垂直 TopDown，非街景人眼摄影。镜头从 [方向] 看向 [方向]，主街在屏幕中主要横向延伸。
空间：主街有可走宽度；[实际巷道/连接路] 向纵深延伸；呈现可读的街角、侧墙、雨篷、前后建筑重叠和有依据的台阶／平台。前景遮挡、中景可走区、远景天际线层次清楚。
美术：清晰的像素人物，像素纹理的简化立体建筑与道具，统一颗粒和材质语言；不做写实背景贴几个像素人物，不用整幅模糊掩盖细节。
光照与景深：真实体积受光、接触阴影、克制的光晕；主角及主要行走区清楚，近远景适度虚化，纵深通路仍可辨认。
角色与生活：三角白帽白衣小巫师，脚底与尺度清晰；按街段证据布置 [候车/卸货/站口出入/停留等]，留出主角路线。车辆按香港道路方向运行。
标识：使用已核实的商铺、港铁出口和站牌位置；重要繁体中文／英文标识预留独立排字区域，生成文字不是最终生产文字。
用途：构图、模块拆分和灯光参考；不是实机截图，不据此推导隐藏几何或真实坐标。
  1. 生成图保存到 assets/blocks/<block_id>/generated/concepts/，附完整提示词、输入参考清单／哈希、工具、输出哈希和已知偏差。先检查镜头是否像 HD-2D、道路是否正确、前后层次是否可走、材质是否过度写实。
  2. 若模型改变路口或楼层，修正引导图／提示词并迭代，不反过来修改真实骨架迁就错误图。概念未达到空间要求时，不进入批量贴图制作。

4. 将概念拆成可实现的资产包

本步至第 5 步必须结合 HD-2D 素材建模与拼装 SOP 执行。概念探索后，先确定灰盒镜头合同，再做 角色方向与动作 和一个商铺模块包；专业依据见 资料索引，不要把试作帧数或像素尺寸当作行业标准。

  1. 建立资产清单，区分复用模块与街区独有物件：地面、路缘、标线、墙面、窗格、建筑转角、雨篷、招牌、公交／汽车、站牌、地铁口、栏杆、树木、道具及人物。
  2. 根据逻辑尺寸、目标镜头和概念生成纹理／图集／精灵；明确像素密度、物理尺寸、正交展开、可平铺边界、透明背景、留边与图集布局。贴图避免烘入不一致的镜头透视；动态受光资产避免画死与场景矛盾的强阴影。
  3. 颜色、发光、透明裁切等需要的通道分别制作和验证；法线、深度、粗糙度不是从一张概念图自动得到的可靠真值。先验收一个商铺与一种地面，再扩展同类资产。
  4. 店名、街名、出口号和路线文字单独排版，替换生成伪字。角色和 NPC 动画检查朝向、足底锚点、帧间体积；车辆检查尺度、朝向及车门位置。
  5. 生成资产放 generated/，手工修订放 authored/，通过资产清单明确最终采用版本。重建脚本不得覆盖 authored/，不得把整幅概念图切层当作完整可行走世界。

完成条件：资产能按清单对应地面、立面、遮挡、灯光和碰撞职责；纹理导入预览正确，不宣称概念图已经是游戏资源。

5. 按需建模并导入 Unity

运行时按 镜头、灯光与景深实施 检查：先无后处理的深度／受光／遮挡，再加景深。Gaussian 只做远景虚化，Bokeh 才是前后景同时虚化的候选；当前 URP 17.3 正交 DOF 存在源码层面的兼容风险，不能默认可用。

  1. 先用 Unity 基础几何和现有模块搭建逻辑骨架；规则路面、简单墙体和碰撞不必绕行 Blender。需要独特地标轮廓、复杂转角、台阶、站口、桥体、车辆或 UV／烘焙时使用 Blender。
  2. Blender 产物保持明确米制尺寸、局部原点、轴向与枢轴；建筑分拆底座、立面、侧面、屋顶／雨篷、招牌和灯具。隐藏侧面按镜头需求补齐，不逐栋恢复不可见的完整内部。
  3. 保存可编辑源文件，并导出当前 Unity 工程实际支持的格式，记录导出设置；不要假设任意模型格式无需导入器即可使用。核对比例、朝向、UV、法线、材质和碰撞，避免原始巨大 GIS 坐标直接进入引擎。
  4. Unity 工程目录未确定时只建立一套明确的工程结构；锁定 Editor／URP／框架／包版本，保留 Assets、.meta、Packages、ProjectSettings，不提交 Library 等缓存。使用现有兼容组件，不并行堆叠输入／角色／镜头控制器。
  5. 游戏世界采用 X=东、Z=北、Y=高度的明确映射，来源数据不变；真实高度与艺术压缩分别记录。使用 3D 碰撞与有证据的跨层连接，不用全局 Y-sort 代替楼层。
  6. 配置区内稳定镜头、纵深跟随与必要镜头区过渡；像素角色使用逻辑根节点＋直立视觉子节点，验证受光、深度写入、裁切和稳定阴影。近景屋檐／树冠采用局部遮挡处理，景深保持主角与可走区清楚。

完成条件：场景在 Unity 内能运行，导入无关键错误，主角可沿骨架行走；仅模型导入成功不算街区完成。

6. 添加香港街道活动

  • 行人：有目的地的行走、等灯、候车、排队与停留；按世界位置和楼层寻路，入口／出口有合理边界，不能从墙里生成。近处完整行为，远处简化。
  • 汽车：按核实的道路方向、车道、信号和停靠空间运行，转弯不穿建筑、过街不撞人；真实车道资料不足时采用明确标注的局部编排路线，不伪称完整交通还原。
  • 公交与站点：按已核对车型／站位组织驶入、减速停靠、开门、下客／上客、队列变化、关门离站。站牌、车辆、车门和人流共用活动状态；不得用两站直线连线代替驾驶路线。
  • 地铁口：人流沿真实可用梯口／入口进出，与人行道和过街点相连；不制作的站内区域作为明确退出／生成边界。站口编号、楼层与运营条件单独核实，不能所有出口套同一通行模板。
  • 生活：按街区加入卸货收货、外卖取餐、雪糕售卖、朋友聚会、清洁或观景等，人物、道具、车辆与空间声源同步；活动有开始、过程、结束，不永久重复单一动作。
  • 声景与时间：视听使用一致的信号和活动状态；昼夜／晴雨影响照明与行为，不能只换滤镜。没有证据的日程标为设计编排，不冒充真实运营时刻表。

完成条件：本街段至少一组完整微活动可观察，交通设施确实运作；只摆站牌、停一辆巴士或放随机巡游者不算完成相应功能。

7. 用主角执行动线并打磨

  1. 固定一条可重复路线及初始状态，实际控制白帽主角执行：主街双向走 → 转入纵深街巷 → 经过设施／人群 → 有开放高差时上下层 → 返回。路线不得只在无障碍空地里绕圈。
  2. 在实际运行场景中检查脚底、碰撞、路缘、墙角、台阶／坡面、桥下遮挡、转角视野与景深；镜头区边界往返，确认输入不反向、镜头不反复跳变。检查暂停、区域切换及位置／楼层读档。
  3. 原地观察至少两分钟，验证本次活动的开始与结束，公交靠站与站口人流不穿模、不堵死主角路线。按本次范围比较昼夜／天气预设；复杂活动未实现则明确列缺口。
  4. 先跑编辑器，再导出本机可运行的独立 Player。记录机器、引擎／包版本、分辨率、可见角色／车辆、灯光、景深设置、帧时与内存；性能目标以当前策划案为准，禁止把编辑器观感称为独立 Player 结果。
  5. 保存关键机位截图、必要的路线录像、运行日志和问题记录到 docs/08-blocks/<block_id>/validation/。有自动化能力就复用脚本／测试路线，但脚本文件存在或测试启动不算通过，必须检查实际返回与画面。
  6. 按证据修复影响空间真实性、行走、遮挡和生活节奏的问题，重跑受影响路线；未涉及的检查无需全量重复。静态好看但无法自然走动时，优先修场景与镜头，不继续堆地标。
  7. 工具、素材或硬件阻塞时保存当前成果、失败证据与可继续的下一步；不得声称已完成尚未执行的行走、截图、导出或性能验证。

8. 最终光照烘焙与复验

先完成空间、贴图、灯位及无景深试走，再做交付用烘焙。提前的小分辨率试烘可以排查 UV、漏光和探针问题，不能代替最终场景的重烘与验收。

  1. 分离静态建筑／地面与动态人物／车辆；为静态网格生成不重叠的 UV2，选择光照贴图密度，小物件按需使用探针。
  2. 配置固定预设：Mixed 主光保留动态直射和阴影，烘焙间接光；固定店内灯可使用 Baked。探针覆盖主街、支路、阴影边界及人物活动高度。
  3. 实际运行烘焙，确认完成且产出 Lightmap、LightingData、探针；保存场景、配置与资产，不把“启动成功”当完成。
  4. 导出独立 Player，核对烘焙数据存在、人物／公交不被烘进静态场景、关闭 DOF 也无明显漏光或接缝，再重跑主角路线和活动。
  5. 日夜各自维护匹配的光照数据；只完成一个预设时锁定该预设。几何、静态材质和灯位改动后重新烘焙。依据与本机结果见 镜头／光照规范。

9. 街区交付与版本记录

每个街区至少有：范围／路线说明、来源 manifest、逻辑骨架、街景参考索引、imagegen 提示词与概念图、资产清单、需要时的 Blender 源与导出、Unity 场景及依赖、验证记录和未解决项。资料／概念／生产资产／实机证据分别标识；分析用项目内 Markdown、独立 HTML 或标准图表。

每次收尾简要报告：完成内容、运行与视觉验证、未完成项、可点击文件路径、commit 与推送状态。概念验收和实机验收分开，用户未认可的画面不能记录为已通过主观美术验收。

HD-2D 素材建模与拼装工作流

调研日期：2026-11-01。适用于本项目像素人物＋立体香港街景的生产，补足 街区还原工作流 第 3–5 步。本文是经资料支持的项目 SOP，尚未通过完整资产样板验证。 原始开发实践、工具能力和我们的取舍见 专业来源与核查记录，角色细节见 多方向与动作生产，镜头与效果见 渲染实施。

1. 制作顺序与停止条件

完整链路：真实骨架／街景取证 → 灰盒与镜头合同 → 概念与资产拆解 → 角色小样＋一个商铺模块包 → Unity 拼装和无后处理试走 → 灯光／景深 → 生活活动 → 独立 Player 验证 → 批量扩展。

概念探索可以先做，但批量角色出帧和建筑精修必须等镜头合同确定。镜头改变后，先复查既有资产，不自动重建覆盖精修源。Gemdrops 的场景制作案例包含先调整镜头／布局、早期复用模块、精修入口小区域后再提升全场景的做法；本项目采用这个“小样先闭环”的生产原则，不照搬其写实背景或世界尺度。CGWORLD 对开发团队的背景制作访谈

每阶段都有可检查产物；失败就回到影响它的上游：脚底错先查角色锚点，建筑转角缺失先补几何，地理错回查来源，模糊问题先检查深度。不能继续堆细节来掩盖根因。

2. 阶段 A：建立镜头与资产合同

输入：街区数据包、实景照片方向与年代、选定主街／连接口、已知地理缺口。

先在约 20–30 米试作范围建立道路、铺面体块和连接巷口，配一个明确身高的白帽占位体。至少检查主街两端和巷道深处，确定主要可见立面、必要侧面、能否读出通道。几何尺寸来自逻辑骨架；构图压缩另存设计变换，不修改原始坐标或无依据加坡。

把以下字段写进该街区资产清单或制作说明：

  • camera_contract：投影、俯角／方位、FOV／距离、跟随范围、目标分辨率、主角屏幕高度、允许出现的镜头区。
  • scale_contract：设计米与 Unity 单位、模块尺寸、原点、坐标轴转换、贴图像素密度测试档位。地面、立面、角色分别记录，不强求一种 PPU 适用于全部对象。
  • asset_contract：来源与许可、源文件、导出格式、材质通道、碰撞／投影／遮挡职责、方向／动作、生成及精修位置。
  • validation_contract：固定机位、试走路线、昼夜条件、必查错误和留存证据。

通过条件：灰盒里能横向往返、深入连接巷道，主角和路缘可读，近远关系成立。输出镜头配置与灰盒截图；仅概念图好看不算通过。

3. 阶段 B：角色小样先跑通

按 角色生产 完成设定转面图 → 游戏俯角方向表 → 站姿 → 步行关键姿势 → 完整循环 → PNG＋JSON → 足底锚点与受光预制体。

先四向试作，斜走和切镜需要时补八向；不把 4／8 向、48–64 像素或 6 帧写成行业硬标准。主角与 NPC 使用同一尺寸和导入合同，但 NPC 的携物、推车、候车等按活动拆动作，不以换色代替动作制作。

通过条件：同一小样中完成横走、纵深进出、停步、转向、墙边遮挡；没有帧间漂移和严重滑步。此时才允许复制到更多 NPC。

4. 阶段 C：建筑与景物怎么建

4.1 按空间职责选形态

  • 近处可绕行物件：商铺转角、站口台阶、雨篷、路缘、巴士／货车等使用真实体积与必要侧面。规则几何可直接在 Unity 制作；复杂轮廓、车辆、独特站口、UV 和烘焙按需 Blender。
  • 平面信息：店名、出口编号、线路牌、广告和窗贴可用独立薄面／贴花，但挂靠实际建筑，不承担整栋楼的碰撞。字形单独排版校对，保留商业和交通信息的真实性。
  • 有限观察的景物：树叶等可试裁切面片，树干保留体积；固定远景可用简化几何或受约束背景卡。必须记录允许机位，镜头接近或转向后露馅就升级资产。
  • 活动道具：手推车、箱筐、雪糕车、站牌、巴士车门等同时考虑人物站位和动作；有开合／转动需求的部分单独分件并设置功能枢轴。

4.2 一个商铺模块包的实际步骤

  1. 参照定尺：从核实的立面宽度、道路／人行道和照片量测关系建立体块；高度无证据时写估计范围。锁定底部基准和转角位置，不用生成图的窗格数当测绘结果。
  2. 按结构拆件：底座／首层立面、墙段／转角、窗格、屋顶／雨篷、橱窗、招牌、灯具。必须共同遮挡或共同活动的部分再合并；不要为了“分层”把每扇固定窗都变成独立高开销对象。
  3. 统一接口：模块端点、楼层基线、墙厚与拼接网格一致；转角有专用件，允许为真实不规则地块制作独有件。模型原点放在约定地面基准；车门、轮子等在关节处另设 pivot。
  4. 模型检查：应用并记录需要的变换，检查法线方向、负缩放、退化面和可见背面；用棋盘贴图检查拉伸。低面数服务轮廓，不以“越少越好”牺牲港式雨篷、栏杆与站口识别特征。
  5. UV 展开：按立面／转角等可编辑区域展开，统一主要可见面的像素密度，给 UV 岛留边；路面／砖墙可平铺，独有店面和招牌另图。Blender 官方提供 UV 缩放、拼岛和布局导出，用导出的 UV 线稿给像素绘制或图生图作位置约束。UV 编辑 · UV Layout
  6. 贴图生产：按目标 UV 画色块和材质纹理，回到模型看接缝／窗格对齐。颜色、alpha、emission 分开验证；法线／粗糙度按需求增加，不把生成图的“深度图”当真值。可平铺贴图检查四边拼接；可见像素应形成有意组织的形状，不能只有照片缩小后的噪点。
  7. 灯光边界：动态受光颜色图避免固定强高光／投影，文字独立校正。若烘焙光照，需要独立、符合烘焙要求的 UV，而不是直接复用有重叠的平铺 UV。
  8. 导出验证：保存 .blend 等可编辑源，输出显式 FBX＋贴图并在 Unity 重建所需材质；不要假定 Blender 节点材质会无损迁移。记录导出／导入轴向、单位和缩放，先用 1 米测试物与带箭头的不对称件验证尺寸和朝向；不能机械照抄网上某组 Forward／Up 参数。Blender FBX 官方文档

交付：模型源、导出模型、UV 布局、贴图与材质通道说明、尺寸／枢轴、碰撞方案、正面／转角预览。图生图出的立面只能作为制作输入；需要透视修正、UV 对齐、补侧面和人工文字校正后才能进入生产。

5. 阶段 D：怎么拼成 Unity 场景

导入当前唯一工程 unity/HongKong/，不新开第二套示例工程。生产源在 assets/blocks/<block_id>/generated/ 或 authored/；选用的运行时副本进入 Unity Assets 并记录源路径／哈希、.meta 和 importer 设置。构建只刷新明确的生成目录，手工 prefab 调整另存变体或手工目录，避免重导出覆盖。

建议预制体职责如下；名称是本项目约定，不声称已经实现：

ShopRoot（地面基准、asset_id）
  Structure（墙体／转角／屋顶）
  Canopy（雨篷与遮挡分组）
  SignsAndLights（招牌／发光／实际灯光）
  Collision（简化碰撞，明确可走／不可走）
  ActivityAnchors（店门、交货、队列或停留位置）

CharacterRoot（3D 移动／碰撞／世界朝向）
  VisualPivot（脚底锚点、方向帧、受光面片）
  ShadowProxy（只有经验证需要时启用）

拼装顺序：

  1. 地面与通行：先路面、人行道、路缘、台阶、碰撞、跨层连接；依据数据骨架摆放。道路绘制层与通行楼层分开。
  2. 建筑体块与接口：替换灰盒为商铺／转角模块；检查接缝、店门宽度、雨篷高度和巷道净空。远景只在已确定的可见范围补足。
  3. 设施与活动空间：港铁口、站牌、栏杆、垃圾桶、货物等按核实位置／明确编排放置；保留排队、卸货和过街空间，再添加装饰密度。
  4. 角色／车辆：导入已通过小样的角色，车辆按世界路线移动并验证转弯可见面。公交服务门、站位、人流锚点共用状态；素材存在不代表运营逻辑存在。
  5. 无后处理试走：先看遮挡、脚底、材质、尺度和拼接，再调光照；若基本画面不成立，不进入批量细化。
  6. 灯光与景深：按 镜头与渲染实施 添加昼夜光照、受控 Bloom、DOF 和镜头区。前中远景是空间职责，不是三张覆盖全场景的 PNG。
  7. 生活闭环：最后加入该街段选定的完整行为和声景，执行主角路线及原地观察；功能验收沿用街区工作流第 6–7 步。

6. 资产交接与 Agent 可复现要求

每个采用的资产至少关联：asset_id、source_ids、source_file、source_hash、generator_or_tool_version、export_settings、runtime_path、dimensions_m、pivot、material_channels、collision_role、occlusion_role、validation_status。角色再附方向／帧／锚点；场景实例另用 instance_id 与现实 place_id。这是应补入资产清单的字段合同，尚无宣称可直接执行的自动化 schema。

Agent 每次只推进一个可验收小包：输入引用 → 可编辑产物 → 导出／导入 → 可视检查 → 记录结果 → commit／push。Aseprite CLI、Blender Python、Unity CLI／Pipeline 可以承接相应自动化，但每次先核实当前安装与接口；有命令模板不等于已安装工具。自动检查尺寸、缺帧、引用与导入错误；人工／Agent 视觉检查负责轮廓、滑步、真实街景和画面质量，两者不能互相替代。

7. 当前首块的闭环门槛

针对弥敦道 × 海防道／A1，下一次进入制作时先完成：一名白帽主角＋一个商铺转角包＋一段主街／巷道连接＋一件近景遮挡物＋站口占位／核实外形。这不是削减 v0.1 范围，而是其前置生产样板。

通过以下检查后再扩成正式街段：

  • 正／背／侧及所需斜向一致，步行和停步不漂；昼夜下白帽可读。
  • 转角、雨篷、路缘、站口具备真实深度，遮挡和碰撞正确；从两个机位都成立。
  • 景深关闭时画面仍成立，开启后主角、通道与重要标识仍清楚；镜头边界往返无跳变。
  • 独立 Player 跑完固定路线，保存截图／录像、配置、日志和可获取的性能数据；美术未获认可就记录为待评审。
  • 重导出生成资产不覆盖手工修订，重进工程能恢复同一画面。

这次调研补上的是制作方法与证据链。像素审美一致性、动画质量、镜头遮挡和整段运行成本仍须以上样板实测，不能宣称“流程写清楚以后只剩机械拼装”。
